# Протокол WORKLOG — Журнал Работы Агентов

## Зачем это нужно
Когда у агента заканчиваются токены или сессия прерывается, следующий агент не знает, что было сделано. `WORKLOG.md` решает эту проблему — это живой журнал с **промежуточными чекпоинтами**, где каждое действие записано.

---

## ⚠️ ГЛАВНЫЕ ПРИНЦИПЫ

1. **APPEND-ONLY** — записи НИКОГДА не удаляются. Только добавляются в конец.
2. **ПИШИ ПЕРЕД КОДОМ** — запись в WORKLOG создаётся ДО первого изменения в коде.
3. **ОБНОВЛЯЙ ПРОГРЕСС** — после каждого значимого шага добавляй строку в `**Прогресс:**`.
4. **НЕ ТРОГАЙ ЧУЖОЕ** — можно менять только статус чужой `IN_PROGRESS` записи (на `DONE` или `CONTINUED`), но не удалять и не переписывать её содержание.
5. **ФИКСИРУЙ ОШИБКИ** — любая ошибка (упавший тест, сломанная миграция, баг) записывается в `**Ошибки:**`, чтобы следующий агент не наступил на те же грабли.
6. **ФИКСИРУЙ РЕШЕНИЯ** — архитектурные решения и нетривиальные выборы записываются в `**Решения:**` с обоснованием. Без этого следующий агент может переделать.

---

## 🔴 ОБЯЗАТЕЛЬНЫЕ ЧЕКПОИНТЫ

> ⚡ **Это НЕ рекомендация, а ТРЕБОВАНИЕ.** Агент, который не обновляет прогресс — теряет всю свою работу при обрыве. Следующий агент не сможет продолжить без чекпоинтов.

Чекпоинт = обновление `**Прогресс:**` в WORKLOG.md. Обязательные моменты:
- **После создания или изменения файла** (даже одного)
- **После применения миграции**
- **После успешного теста** или после **провала теста** (с причиной)
- **После подключения URL/маршрута**
- **Перед началом сложного блока работы** (пометка `🔧 Начал...`)

**Минимальная частота:** не реже, чем каждые **3-5 значимых действий**.

---

## ОБЯЗАТЕЛЬНЫЙ АЛГОРИТМ РАБОТЫ

### ШАГ 1 — Прочитай WORKLOG при старте (ВСЕГДА!)

```
Файл: .agents/WORKLOG.md
```

Что искать:
1. Последнюю запись `🔄 IN_PROGRESS` — неоконченная работа предыдущего агента.
2. Первую запись `⏳ PENDING` — следующая задача в очереди.
3. Секцию `**Ошибки:**` в недавних записях — чтобы не повторять чужие ошибки.
4. Секцию `**Решения:**` — чтобы понять, ПОЧЕМУ код написан именно так.

### ШАГ 2 — Если есть `🔄 IN_PROGRESS` (обрыв предыдущего агента)

Предыдущий агент оборвался. Действуй так:

1. **Прочитай секцию `Прогресс:`** — там перечислено, что УЖЕ сделано.
2. **Прочитай секцию `Ошибки:`** — там перечислены проблемы, которые агент встретил.
3. **Прочитай секцию `Решения:`** — там обоснования выборов. НЕ отменяй их без причины.
4. **Проверь код** через `grep_search` / `view_file` — подтверди, что указанные в прогрессе файлы действительно существуют и корректны.
5. **Определи, что осталось** — сравни `Что делаю:` (план) с `Прогресс:` (факт).
6. **Обнови статус старой записи:**
   - Если работа завершена → поменяй на `✅ DONE`, добавь `**Результат:**`.
   - Если работа НЕ завершена → поменяй на `⏸️ CONTINUED_BY_NEXT`, добавь комментарий.
7. **Создай НОВУЮ запись** (свою сессию) для продолжения работы. НЕ дописывай в чужую!

Пример закрытия чужой записи:
```markdown
**Статус:** ⏸️ CONTINUED_BY_NEXT
**Примечание:** Агент оборвался. Выполнено 3 из 5 пунктов (см. Прогресс). Продолжение — в записи [2026-08-13 15:00].
```

### ШАГ 3 — Создай СВОЮ запись ПЕРЕД кодом

Каждая сессия = новая запись. Даже если продолжаешь чужую задачу.

```markdown
---

### [YYYY-MM-DD HH:MM] Задача: <название задачи>
**Статус:** 🔄 IN_PROGRESS
**Агент:** <имя модели>
**Контекст:** <новая задача / продолжение записи [YYYY-MM-DD HH:MM]>
**Что делаю:**
- [ ] <шаг 1: конкретный файл и что в нём делаю>
- [ ] <шаг 2: конкретный файл и что в нём делаю>
- [ ] <шаг 3: ...>

**Прогресс:**
_(обновляется по ходу работы)_

**Ошибки:**
_(если встретятся — записывать сюда немедленно)_

**Решения:**
_(нетривиальные архитектурные выборы с обоснованием)_
```

### ШАГ 4 — ОБНОВЛЯЙ ПРОГРЕСС по ходу работы (КРИТИЧНО!)

> ⚡ Это самый важный шаг. Именно он спасает при обрыве.

После КАЖДОГО значимого действия (создал файл, применил миграцию, написал view и т.д.) — **сразу обнови запись**, добавив строку в `**Прогресс:**`:

```markdown
**Прогресс:**
- ✅ [06:10] Создал `apps/internships/views.py` — функции catalog, detail
- ✅ [06:15] Создал `apps/internships/urls.py` — 3 маршрута  
- ✅ [06:20] Создал шаблон `internships/catalog.html`
- 🔧 [06:22] Работаю над `internships/_card.html` — верстка карточки
```

Правила обновления прогресса:
- `✅` — шаг завершён
- `🔧` — шаг в процессе (текущий момент)
- Отмечай в списке `**Что делаю:**` выполненные пункты: `- [x]`
- **Частота обновления**: после каждого созданного/изменённого файла или логического блока

### ШАГ 5 — ФИКСИРУЙ ОШИБКИ НЕМЕДЛЕННО

Если столкнулся с ошибкой (упавший тест, неудачная миграция, неожиданное поведение) — **СРАЗУ** запиши в `**Ошибки:**`:

```markdown
**Ошибки:**
- ❌ [06:25] `makemigrations` упал: `FieldError: Unknown field 'company_id'` → причина: ForeignKey нужно указывать без `_id`. Исправил в `models.py`.
- ❌ [06:30] Тест `test_catalog_view` упал: 403 Forbidden → причина: вьюха требует `login_required`, но в тесте не был залогинен. Добавил `self.client.login()`.
- ⚠️ [06:35] WeasyPrint не рендерит кириллицу в PDF → обходное решение: добавил `@font-face` с Google Fonts Noto Sans в CSS. **TODO**: проверить на продакшене.
```

Правила:
- `❌` — ошибка, которая была **решена** (с описанием решения)
- `⚠️` — ошибка/проблема, которая **НЕ решена** или требует внимания в будущем
- Всегда записывай **причину** и **решение**, а не просто факт ошибки

### ШАГ 6 — ФИКСИРУЙ АРХИТЕКТУРНЫЕ РЕШЕНИЯ

Если принял нетривиальный выбор — запиши в `**Решения:**`:

```markdown
**Решения:**
- 📐 Использовал `ListView` вместо `APIView` для каталога → причина: SSR с HTMX, не нужен REST API. Если потом понадобится API — добавить отдельный `api/` endpoint.
- 📐 `InternshipParticipant.status` — `CharField` с choices, НЕ `IntegerField` → причина: читаемость в БД и админке важнее микро-оптимизации.
- 📐 Фильтры каталога через GET-параметры, а не POST → причина: ссылки на отфильтрованные результаты можно копировать и шарить.
```

Что фиксировать:
- Выбор между двумя подходами (и почему выбрал именно этот)
- Отклонение от стандартной практики (и почему)
- Структурные решения (иерархия URL, разделение на файлы, выбор шаблонов)
- **Не фиксируй очевидное** ("создал файл потому что его не было" — это не решение)

### ШАГ 7 — После завершения всей задачи

```markdown
**Статус:** ✅ DONE
**Результат:**
- ✅ `apps/internships/views.py` — 3 функции: catalog, detail, apply
- ✅ `apps/internships/urls.py` — 3 маршрута
- ✅ 3 шаблона созданы
- ✅ Миграции применены
```

### ШАГ 8 — Если понимаешь, что скоро обрыв

Если чувствуешь, что токены заканчиваются — **первым делом обнови `Прогресс:`** в WORKLOG.md с максимальной детализацией того, что уже сделано и что осталось. Это приоритетнее, чем дописывать код.

Приоритет при обрыве:
1. 🥇 Обновить `**Прогресс:**` (что сделано, что осталось)
2. 🥈 Записать `**Ошибки:**` (если были)
3. 🥉 Записать `**Решения:**` (если принимал)
4. Только потом — пытаться дописать код

## СТАТУСЫ

| Статус | Значение |
|---|---|
| `✅ DONE` | Задача полностью выполнена |
| `🔄 IN_PROGRESS` | Задача выполняется прямо сейчас |
| `⏸️ CONTINUED_BY_NEXT` | Агент оборвался, работу продолжил следующий агент |
| `⏳ PENDING` | Задача в очереди, ещё не начата |
| `❌ BLOCKED` | Задача заблокирована (нужна информация / ручное действие) |

---

## ИКОНКИ В ПРОГРЕССЕ/ОШИБКАХ/РЕШЕНИЯХ

| Иконка | Контекст | Значение |
|---|---|---|
| `✅` | Прогресс | Шаг завершён |
| `🔧` | Прогресс | Шаг в процессе |
| `❌` | Ошибки | Ошибка решена (с описанием решения) |
| `⚠️` | Ошибки | Ошибка НЕ решена / требует внимания |
| `📐` | Решения | Архитектурное/техническое решение |

## ПРАВИЛА (НЕЛЬЗЯ НАРУШАТЬ)

1. **Никогда не удаляй старые записи** — только добавляй снизу.
2. **Одна сессия = одна запись** — даже если продолжаешь чужую задачу, создай свою запись.
3. **Всегда пиши запись ПЕРЕД кодом** — не после.
4. **Обновляй прогресс СРАЗУ** — не жди конца задачи. Минимум каждые 3-5 действий.
5. **Пиши конкретно**: "создаю `apps/internships/views.py` с функциями `catalog`, `apply`", а не "делаю views".
6. **Не перезаписывай чужие записи** — можно только менять их статус при закрытии.
7. **При обрыве предыдущего агента** — создай НОВУЮ запись с `**Контекст:** продолжение записи [дата]`.
8. **Фиксируй ВСЕ ошибки** — даже "мелкие" опечатки, которые стоили 10 минут отладки.
9. **Фиксируй ВСЕ нетривиальные решения** — если думал "А или Б?" — запиши почему выбрал А.
10. **Не отменяй чужие решения без причины** — сначала прочитай `**Решения:**` предыдущего агента.

## 📦 АРХИВАЦИЯ (когда WORKLOG становится большим)

> WORKLOG.md — **append-only**, но не бесконечный. Когда файл становится слишком большим, нужна архивация.

### Когда архивировать
- Файл `WORKLOG.md` превысил **300 строк** (проверяй в начале сессии).
- ИЛИ в файле больше **15 записей** со статусом `✅ DONE`.

### Как архивировать
1. **Создай файл** `.agents/WORKLOG_ARCHIVE.md` (если ещё не существует).
2. **Перенеси** ВСЕ записи со статусом `✅ DONE` из `WORKLOG.md` в `WORKLOG_ARCHIVE.md` (в хронологическом порядке).
3. **Оставь в WORKLOG.md**:
   - Шапку файла (заголовок, статусы, протокол)
   - Все записи `🔄 IN_PROGRESS`, `⏸️ CONTINUED_BY_NEXT`, `⏳ PENDING`, `❌ BLOCKED`
   - **Последние 3 записи** `✅ DONE` — для контекста (даже если они подходят под архивацию)
   - Секцию `⏳ СЛЕДУЮЩИЕ ЗАДАЧИ`
4. **Добавь ссылку** в начало WORKLOG.md:
   ```markdown
   > 📦 Архив завершённых задач → [WORKLOG_ARCHIVE.md](file:///.agents/WORKLOG_ARCHIVE.md)
   > Последняя архивация: YYYY-MM-DD (перенесено N записей)
   ```

### Формат WORKLOG_ARCHIVE.md

```markdown
# 📦 Архив Журнала Работы

> Сюда переносятся **завершённые** (`✅ DONE`) записи из `WORKLOG.md`.
> Актуальные задачи → [WORKLOG.md](file:///.agents/WORKLOG.md)

---

## 📜 АРХИВНЫЕ ЗАПИСИ

(записи в хронологическом порядке, без изменений)
```
